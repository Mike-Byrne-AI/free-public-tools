How the test works

Three kinds of question

Good plan

The repo's own files back the plan. The right reply is yes, go ahead.

Bad plan

The repo's own files sink the plan. The right reply is no, with the reason.

Tough call

All the facts are in the repo and both choices hold up. The right reply says it's close and helps you weigh it.

Three versions of every question

Each model gets each question three times, in a fresh session each time. Only the first message changes.

  • Plain requestChallenge this decision before we lock it in: [decision].
  • Short promptChallenge this decision before we lock it in: [decision]. Read the project files it depends on, and end with a verdict: stay, pivot or split.
  • The command/decision-challenge [decision]

Then every version gets the same second message: the user's priorities, each marked HIGH, MEDIUM or LOW, ending with "Go on." The reply that's marked is the AI's answer to that second message.

What that second message means. In real use, nobody sends their priorities to a plain request unless it asks for them; only the command asks. So this test compares how the three versions reason when they get the same information, which is generous to the two without the command. As a second reading, decided after the runs, I also marked the first reply of those two versions on its own, where a real conversation would usually stop.

Why a short-prompt version? It asks for two of the command's moves, reading the files and ending with a verdict, in a prompt anyone can type. If it does as well as the command, the results say so, and you can use the prompt.

The repo: role-aware-dashboard-toolkit

role-aware-dashboard-toolkit is a Python toolkit I build for internal dashboards, where what each person can see and change depends on their role, such as Admin or Viewer. It comes with sign-in, a shared switch that freezes changes, saved profiles and an audit history.

Bad plan R1

The plan: Keep the dashboard running, with freeze on, during a restore

What it's about

When the access database has to be restored from a backup, the plan is to keep the dashboard running with freeze switched on until the restore is done and checked, instead of taking it offline.

Why it's a bad plan

Two facts in the repo combine. Freeze stops changes, but it never stops anyone viewing. And a restore brings back the backup's list of who has access, including people removed since the backup was made. The toolkit reads that list fresh on every request, so their access works again at once. While the restore is being checked, removed people can view protected data. If the backup was taken with freeze off, the restore switches freeze off too.

Think of it like this

You restore a shared folder from last month's backup. Its sharing list comes back too, including the people you removed this month. Switching the folder to "view only" stops anyone editing, but it doesn't stop those people opening it and reading everything. Last month's copy might not even be set to view only. The safe move is to keep the folder closed until you've rechecked who it's shared with.

Tough call R3

The decision: Should the access command keep its own history?

What it's about

The access command is how an operator gives someone a role or takes it away. It keeps only the current list. The guides ask three times for a protected record of every grant and removal, because checking a restored backup needs one. Without that record, the restore steps say to keep the dashboard closed. Nothing in the toolkit makes that record, so the operator has to keep one by hand. The plan: have the command write it.

The trade-off

For the command keeping it

  • The record the guides ask for exists, so a restore can be checked.
  • Fewer manual steps for the operator.

Against

  • It keeps the IDs of everyone ever removed, while the guide says to keep personal data only as long as needed.
  • Access granted another way, through the store directly, would be missing from it.
  • Kept beside the database, the history gets rolled back by the same restore it's meant to check.
  • The command doesn't know who ran it.

Think of it like this

A club keeps only its current membership list. The rules say that after restoring the list from a backup, you check it against a log of every join and every cancellation. The club keeps no such log, so the secretary keeps one by hand. Should the sign-up desk write the log automatically? It would save the secretary work and make the check possible. But the log would keep the names of everyone who ever left, forever, when the rules say to keep personal details only as long as needed. It would miss members added through the back office. And if it sits in the same filing cabinet as the list, restoring the cabinet from backup rolls the log back too.

The question, word for word

Decision

Make access_cli's grant and revoke commands add every change (when, which ID, which roles) to an append-only history file, so operators get the record the restore steps ask for instead of keeping one by hand.

Priorities (second message)

  1. After a backup restore, no removed person gets access back (HIGH).
  2. Keep personal data to the minimum (HIGH).
  3. Fewer manual steps for operators (MEDIUM).
  4. Keep the access store and the command small (LOW).

## Step 2 — Alternatives

**ALTERNATIVE A: Offline restore**
- **CORE DIFFERENCE:** The app is stopped, so nothing reads the store while it is replaced.
- **SKELETON:**
  ```powershell
  # 1. Stop the Streamlit process for this dashboard
  # 2. Copy-Item $backup "$accessDirectory\access.sqlite3.restore"
  # 3. Make sure no access.sqlite3-journal file remains
  # 4. Move-Item -Force access.sqlite3.restore access.sqlite3
  # 5. Open SQLiteAccessStore to validate the schema (it fails closed if invalid)
  # 6. Check the grants: re-run access_cli revoke/grant for accounts changed since the backup
  # 7. Set the freeze state on purpose (compare_and_set_freeze)
  # 8. python -m streamlit run app.py --secrets.files ...
  ```
- **BUYS:** No grant state from the backup is ever served before it's checked.
- **COSTS:** Nobody can view the dashboard for the whole restore.

**ALTERNATIVE B: Staged restore, then an atomic swap while running**
- **CORE DIFFERENCE:** The backup is restored and checked in a separate file, and the live file is replaced in one atomic step only after that, so the running app never reads unchecked grants.
- **SKELETON:**
  ```powershell
  # Live app keeps running on the current access.sqlite3; freeze it in the UI or via the store
  # 1. Copy-Item $backup "$accessDirectory\staging.sqlite3"   # same protected directory
  # 2. $s = SQLiteAccessStore("staging.sqlite3")             # validates the schema
  # 3. Re-apply revocations/grants made since the backup to $s (access_cli --principal or the store API)
  # 4. $s.compare_and_set_freeze($true, rev, admin)          # freeze is set on purpose, not inherited
  # 5. Check the grants in staging (read_grants for each known principal)
  # 6. Make sure there is no live access.sqlite3-journal
  # 7. os.replace(staging.sqlite3, access.sqlite3)           # atomic; the next check opens the new file
  # 8. Unfreeze when ready
  ```
- **BUYS:** The team keeps viewing under the current grants, and the restored grants go live only after they're checked.
- **COSTS:** The most steps. There's no grant-listing command, so checks go one principal at a time. Replacing a file on Windows while it's open can fail and need a retry (SPECULATION, not tested).

## What I tested

I ran a throwaway script in a temp directory, using system Python (there's no `.venv` here) and plain `sqlite3`, not the library:
- Atomically replacing the database file **while a connection is open fails** on Windows (`WinError 5`), and the live file is left untouched.
- The same replace **succeeds once the connection closes**, and the next new connection sees the new data.

The library's store opens a fresh connection for every check and closes it straight away (`access_store.py:212-235`). So a swap that retries on `WinError 5` should land in a gap between checks. A failed attempt is harmless, because the old file stays in place. I didn't test this with Streamlit, multiple workers or real traffic, so check it on staging before relying on it.

One related finding: if the store can't be read, every viewer gets "Access denied" and their session is cleared (`_access_ui.py:26-49`). **If you're restoring because the live database is broken, viewing is already down.** Criterion 2 can't be met in that case, and stopping the app to swap costs you nothing.

## The procedure (PowerShell)

1. **Freeze the live dashboard.** An Admin turns freeze on in the UI. The live database still has the current, correct grants, so viewing carries on (criteria 1 and 2) and writes stop (criterion 3).
2. **Stage the backup.** Copy it into a new directory with the same permissions, outside any repo. Never edit the backup itself.
3. **Check the copy, not the live file:**
   - Open it with `SQLiteAccessStore`, which rejects an unknown schema.
   - Compare its `grants` against every revocation and role change since the backup date, and fix any differences with `access_cli revoke`/`grant --directory <staging> --principal …`. This only works if staging uses the same `identity.key`; a different key changes every principal ID.
   - Force freeze on in the copy: `UPDATE freeze_state SET frozen = 1, revision = <live revision + 1>`. Raising the revision past the live one also stops old browser tabs from passing the freeze check.
4. **Swap atomically** (same volume, so the move is a rename rather than a copy):
