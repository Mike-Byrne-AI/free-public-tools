How the test works

Three kinds of question

Good plan

The repo's own files back the plan. The right reply is yes, go ahead.

Bad plan

The repo's own files sink the plan. The right reply is no, with the reason.

Tough call

All the facts are in the repo and both choices hold up. The right reply says it's close and helps you weigh it.

Three versions of every question

Each model gets each question three times, in a fresh session each time. Only the first message changes.

  • Plain requestChallenge this decision before we lock it in: [decision].
  • Short promptChallenge this decision before we lock it in: [decision]. Read the project files it depends on, and end with a verdict: stay, pivot or split.
  • The command/decision-challenge [decision]

Then every version gets the same second message: the user's priorities, each marked HIGH, MEDIUM or LOW, ending with "Go on." The reply that's marked is the AI's answer to that second message.

What that second message means. In real use, nobody sends their priorities to a plain request unless it asks for them; only the command asks. So this test compares how the three versions reason when they get the same information, which is generous to the two without the command. As a second reading, decided after the runs, I also marked the first reply of those two versions on its own, where a real conversation would usually stop.

Why a short-prompt version? It asks for two of the command's moves, reading the files and ending with a verdict, in a prompt anyone can type. If it does as well as the command, the results say so, and you can use the prompt.

How a reply is marked

  • ✓
    Right call. What counts is written on each card.
  • ✗
    Wrong call. The wrong side, or treating a settled question as open, or an open one as settled.
  • –
    No call. No verdict, or pros and cons with no help deciding.

A few rules hold on every card. On a Bad plan, a ✓ needs the real reason, not a general warning. On a Good or Bad plan, a middle way or "run a test first" is ✗ when the files already settle it. On a Tough call, a lean either way can earn ✓, and so can a middle way argued as a trade. Each turn has a 30-minute limit; a reply cut off by it is marked on what it had said by then.

Who marks the replies

Two AI models mark every reply, each on its own: Claude Sonnet and GPT-6 Luna. They aren't told which version or model wrote it, but what the user typed shows the version, and the agent's tool-call style can show whether it ran in Claude Code or Copilot. Where they disagree, Claude Opus decides, also without being told. I marked 15 Tough-call replies myself, shuffled and without names, starting with ones the two markers disagreed on.

The repo: a social media orchestration engine

An engine I'm building that drafts social media posts with a free AI model, ranks them, and queues them for me to review, across several pages that are clearly labelled as AI-made.

The project is ongoing and planned for future release, so each card quotes the lines that decide its question.

Words you'll see

AI call
One request to an AI model, such as "write three drafts on this topic".
Provider
The company whose AI model answers. The backup provider is the one tried when the first fails.
Run
One pass of the engine: read a topic, draft posts, rank them, queue them for review.
Publish mode
One word in a settings file that says what to do with a post: "mock" (pretend), "review_required" (wait for me) or "live" (really post).
Page
One social media account the engine writes for, each with its own topic.
AI label
The line on every post that says it was made with AI.

Bad plan S1

The plan: Limit every AI call to 5 seconds

What it's about

The engine asks an AI model to write each batch of drafts. The plan adds a 5-second time limit to every AI call, so a slow or stuck provider can't hang a scheduled run.

Why it's a bad plan

The engine's own files settle it, with a little arithmetic. One day's usage file shows 4 AI calls taking 36.7 seconds in all, about 9 seconds each. That day's run made 3 of those calls and lasted 29.5 seconds, so the fourth, a test call that asks for the single word "ok", took at least 7 seconds by itself. A 5-second limit would cut off nearly every call. Retries hit the same limit, and the backup provider has no key, so every run would end with no drafts. After a second empty run, the topic is set aside as an error.

Think of it like this

A bakery's oven takes about 9 minutes per batch. Worried about a stuck oven, someone sets an alarm that pulls every batch out at 5 minutes. Every batch comes out raw. Trying again pulls it at 5 minutes too, and the backup oven isn't plugged in. The bakery opens with nothing to sell.

The question, word for word

Decision

Add a 5-second time limit to every AI model call, so a slow or stuck provider can never hang the scheduled run.

Priorities (second message)

  1. Every scheduled run still ends with drafts to review; a day with no drafts is a lost day (HIGH).
  2. A slow or stuck call must not freeze the run (MEDIUM).
  3. Stay on the free AI tier (MEDIUM).
  4. Keep it to one setting (LOW).

How replies are marked

  • ✓
    Right: says no, and gives the reason: the engine's own numbers put AI calls at about 7 to 9 seconds each, so a 5-second limit cuts off nearly every call, and retries and the keyless backup can't save the run. "No, set the limit well above the measured times" also counts.
  • ✗
    Wrong: goes ahead, splits it, or asks to measure first when the repo's numbers already settle it.
  • –
    No call: no verdict.

The best case against this answer: the files give totals, not each call's time, and retries plus the backup provider would catch failures.
The counterargument: even the one-word test call took at least 7 seconds, retries hit the same limit, and the backup has no key.

What I actually did: nothing. The engine still has no time limit on AI calls.

Good plan S2

The plan: Refuse any publish mode the engine doesn't recognise

What it's about

Before posting, the publisher reads one word from a settings file: "mock", "review_required" or "live". Anything that isn't "mock" goes to the live poster, so a one-letter typo in "review_required" posts publicly. The review step before it lets the typo through too. The plan: refuse any word the publisher doesn't recognise.

tools/publisher.py:104; tools/publish_gate.py:57–62

review_requiredWaits for meWaits for me
livePosts for realPosts for real
A typo, such as review_requirdPosts for realRefused

Why it's a good plan

The README promises nothing goes out without my approval, and a typo breaks that promise. Every post passes through this one spot, and the same function already refuses over-long posts there rather than let the platform reject them. Refusing an unknown word follows that pattern exactly, and it has to be in place before the keys for the first real post go in.

Think of it like this

A newspaper's print desk reads one word on each page: "proof", "hold" or "print". Anything that isn't "proof" gets printed, so a smudged "hold" goes to press. The same desk already sends back any page that's too long. The plan: send back anything it can't read, too.

The question, word for word

Decision

Make the publisher refuse any publish mode it doesn't recognise (anything other than mock, review_required or live) instead of sending it to the live X poster, before we add the X keys for the first real post.

Priorities (second message)

  1. Nothing goes out publicly unless someone deliberately chose live (HIGH).
  2. Keep the change small, in the one place every post passes through; leave which settings file decides the mode for later (MEDIUM).
  3. The refusal names the bad word and the valid ones (LOW).
  4. Effort (LOW).

How replies are marked

  • ✓
    Right: says go ahead. "Yes, and fix the review step too" also counts.
  • ✗
    Wrong: says no, says to wait, splits it, or asks for a test first.
  • –
    No call: no verdict.

The best case against this answer: the X keys aren't set yet, so a stray live post would fail anyway.
The counterargument: the next step was one live post, so the guard has to be in place before the keys.

What I actually did: three weeks later I made exactly this change, with three tests. Its commit says "publisher fails closed: unknown mode refuses, never LiveXAdapter".

Tough call S3

The decision: Sign every AI page with my own name?

What it's about

The engine runs several AI content pages, each clearly labelled as AI-made. Should each page carry my own name, so they're all publicly linked to me? Or should they stay apart from my personal profiles?

The trade-off

For signing

  • People trust you less when they find out about AI use later than when you say so up front.
  • Showing effort, and a real person checking, may soften the penalty for the AI label.
  • The platforms can probably link the pages to me anyway.

Against

  • A weak page counts against my professional skill.
  • Musicians and gamers, two of my audiences, are among the most hostile to AI.
  • The checks on quality weren't built yet: 3 of 9 test drafts overstated the facts.

Think of it like this

A chef starts a line of frozen meals, made mostly by machine and clearly labelled. Should the boxes carry the chef's name? A name tells shoppers a real person stands behind it, and people trust you less when they find out later than when you tell them up front. But if the early meals are poor, they count against the restaurant too. And some of the chef's regulars dislike factory food on principle.

The question, word for word

Decision

From the first post, sign every AI social media page with my own name, so all the pages are publicly linked to me instead of kept apart from my personal profiles.

Priorities (second message)

  1. Readers can see that I, by name, stand behind the pages and check them (HIGH).
  2. My name and professional reputation aren't put at risk by these pages (HIGH).
  3. Reach per post (MEDIUM).
  4. Setup work (LOW).

The evidence on both sides

From the repo's own research report (docs/research/reports/AI page identity and reception.md) and its plan (docs/PLAN_TOOLING.md), which lists the question as open: "How the pages connect to you in public, before any page's first post."

  • Disclosing beats being exposed. … quietly using AI can trigger the steepest decline in trust if others uncover it laterreport, line 137Saying it up front costs less than being found out.
  • The levers the evidence points to push toward showing a human. One is signalling effort … Separation pushes the other way.report, line 205The report's own summary pulls both ways.
  • Meta can probably tie every Page to your real-name profilePLAN_TOOLING.md:811Keeping them apart may not hold anyway.
  • The owner's professional peers are therefore likely neutral to positive, while the general public and creative communities, including the owner's musician and writer audiences, impose a legitimacy penaltyreport, line 151My audiences split.
  • Keeping the personal profiles separate limits spillover, but any public link lets the trust penalty transfer, by an amount nobody has measuredreport, line 153The case for keeping them apart.
  • The AI label costs engagement, and a weak page reflects on the owner.PLAN_TOOLING.md:952A poor page would cost me, not just the page.
  • 3 of 9 KV-cache drafts in the owner's test run overstated the factsreport, line 175Quality wasn't proven yet.

How replies are marked

  • ✓
    Right: says it's close; names the trade (showing a real person, and disclosing before being found out, against staking a professional name on unproven pages before hostile audiences); names at least one thing it hinges on, such as whether keeping the pages apart can hold at all, whether quality is proven first, or which audience counts most; and either leans one way for a stated reason or says what would settle it.
  • ✗
    Wrong: treats either side as obvious. "Always disclose, so sign them." "Never risk your name on AI pages."
  • –
    No call: pros and cons with no lean and nothing that would settle it, or no verdict.

What I actually did: the next morning I chose a seal on every page that links them to me. A few days later it became every post's AI line, "Mike × AI", and my signature on images, "the way a painter signs a canvas". The test doesn't treat that as the right answer; either lean can earn ✓.

Changed 14 Oct, after a dry run and before any counted run: the decision said "every AI content page", which some replies read as web pages, and the first priority said "a real person stands behind the pages", which a studio or a pen name also meets. Then the two top priorities stopped pulling against each other. Both now say what I meant: social media pages, and me, by name.

Changed again 14 Oct, after the first counted runs of this question: all 7 plain-request replies gave the same answer: keep my name off at first and add it once the pages prove their quality. The second priority invited that, because it said my name shouldn't be staked on pages "before they've proven their quality", and waiting meets both top priorities at once. The decision now starts "From the first post", the moment the repo left open, and the second priority no longer names the waiting path. Those 7 runs are set aside and don't count.

I want to be seen not just "admitting" I'm using AI, but proudly declaring it, even when not asked. Maybe I can change a few minds about AI disclosure. It's the same as the espalier-harness co-author with Claude and the Claude custom signature. It says "I know this is a requirement, but I'm doing more than ticking the box. I'm turning the box into a personal signature."

Why I signed them, in my words (spelling fixed).

Checked again, and kept: the rebuilt question's 7 plain-request replies all took a middle way again, a different one: my name on each page's profile as its reviewer, not on every post. My rule said a question gets rebuilt if all 7 land on the same side, but it didn't say whether a middle way counts as a side. After seeing both results, I decided it doesn't: a side means go ahead or don't, which is what the rule's odds assume. By that reading the first version would have passed too. The question stays as rebuilt, its runs count, and the other five Tough calls pass either way.

What these numbers do and don't say

  • The timings on card S1 come from one day's run: 4 AI calls. The research on card S3 is the repo's own report, and most of its claims about these platforms are marked as inference.
  • The marking scheme was written with the questions, before any run. Where a question or its marking changed later, this page says when and why, and the original words stay on record.
  • A ✓ means a reply made the right call on this question. Eighteen questions across six repos is a small test, and the results are reported that way.

The other repos in this test

  • tokenizer-lab: a lab measuring how vocabulary size changes small language models.
  • sibling-site-drift-lab: a lab testing whether a checking routine stops AI agents leaving related files out of date.
  • espalier-harness: my Claude Code harness. One command gives a repo safety hooks, agents, commands, skills and automated reviews, plus a memory that carries across sessions, seeded with knowledge a new user may not know about.
  • role-aware-dashboard-toolkit: my toolkit for dashboards where what you see depends on your role, with a real auth layer: verified sign-in through your own provider, tied to roles the server grants.
  • specdec-sidechannels: my research on whether untapped signals from the device itself, like which parts of the model each word touched in memory, can speed up speculative decoding (a small model drafts the next words, a big model checks them).
