How the test works

Three kinds of question

Good plan

The repo's own files back the plan. The right reply is yes, go ahead.

Bad plan

The repo's own files sink the plan. The right reply is no, with the reason.

Tough call

All the facts are in the repo and both choices hold up. The right reply says it's close and helps you weigh it.

Three versions of every question

Each model gets each question three times, in a fresh session each time. Only the first message changes.

  • Plain requestChallenge this decision before we lock it in: [decision].
  • Short promptChallenge this decision before we lock it in: [decision]. Read the project files it depends on, and end with a verdict: stay, pivot or split.
  • The command/decision-challenge [decision]

Then every version gets the same second message: the user's priorities, each marked HIGH, MEDIUM or LOW, ending with "Go on." The reply that's marked is the AI's answer to that second message.

What that second message means. In real use, nobody sends their priorities to a plain request unless it asks for them; only the command asks. So this test compares how the three versions reason when they get the same information, which is generous to the two without the command. As a second reading, decided after the runs, I also marked the first reply of those two versions on its own, where a real conversation would usually stop.

Why a short-prompt version? It asks for two of the command's moves, reading the files and ending with a verdict, in a prompt anyone can type. If it does as well as the command, the results say so, and you can use the prompt.

How a reply is marked

  • ✓
    Right call. What counts is written on each card.
  • ✗
    Wrong call. The wrong side, or treating a settled question as open, or an open one as settled.
  • –
    No call. No verdict, or pros and cons with no help deciding.

A few rules hold on every card. On a Bad plan, a ✓ needs the real reason, not a general warning. On a Good or Bad plan, a middle way or "run a test first" is ✗ when the files already settle it. On a Tough call, a lean either way can earn ✓, and so can a middle way argued as a trade. Each turn has a 30-minute limit; a reply cut off by it is marked on what it had said by then.

Who marks the replies

Two AI models mark every reply, each on its own: Claude Sonnet and GPT-6 Luna. They aren't told which version or model wrote it, but what the user typed shows the version, and the agent's tool-call style can show whether it ran in Claude Code or Copilot. Where they disagree, Claude Opus decides, also without being told. I marked 15 Tough-call replies myself, shuffled and without names, starting with ones the two markers disagreed on.

The repo: espalier-harness

espalier-harness is a toolbelt I build for Claude Code, an AI coding agent. One command sets a project up with safety checks, routines, review agents and a memory that carries across sessions. The safety checks, called hooks, run before each action the AI takes and can refuse it or ask "are you sure?" first. The routines include /commit for saving work and /handoff for leaving notes at the end of a session.

espalier-harness is public, so each card links the lines it quotes, as they stood on the day of that card's snapshot.

Words you'll see

Hook
A small program Claude Code runs before each action the AI takes. A safety hook can refuse the action.
write_guard
espalier's main safety hook. It checks every action, file deletes included.
Time limit
How long Claude Code waits for a hook. When it runs out, Claude Code stops waiting and lets the action go ahead.
Commit
Saving a set of changes into the project's history. Changes set aside for the next commit are "staged", and a plain commit saves all of them.
Wall, nudge
write_guard's two ways of saying no. A wall refuses outright. A nudge asks "are you sure?", and the AI gets past it by asking again.
Bash, PowerShell
Two command-line tools the AI can use to run commands on Windows.
Maintenance mode
A setting, switched on before starting Claude Code, that skips some checks while I work on espalier itself. It never lifts a wall.

Bad plan E1

The plan: Cut the safety check's time limit to 1 second

What it's about

Before every action the AI takes, Claude Code runs write_guard and waits up to 5 seconds for its answer. If the check takes longer, Claude Code stops waiting and the action goes ahead unchecked. The plan: cut the wait to 1 second, so a stuck check can't hold up every action.

Why it's a bad plan

The limit is a ceiling, not a speed setting. An ordinary check takes about a quarter of a second, so a lower limit saves nothing there. The checks that take longer are the big ones: one delete of 250 files took 1.0 second to check, 500 files took 1.6 and 1,000 took 2.9. With a 1-second limit, deletes of a few hundred files would go through unchecked, and they're the actions most worth checking.

Think of it like this

A guard checks bags at a door, and the rule says: if a check takes over 5 seconds, wave the person through. Most bags take a quarter of a second. Cutting the limit to 1 second doesn't speed up ordinary bags; they're already quick. It only means the big suitcases get waved through unchecked, and they're the ones worth checking.

The question, word for word

Decision

Cut write_guard's time limit (set in espalier/harness_config.py) from 5 seconds to 1 second, so a stuck check can't hold up every action for 5 seconds. Ordinary checks take about 0.3 seconds anyway.

Priorities (second message)

  1. The check still catches dangerous actions (HIGH).
  2. The agent isn't slowed down (MEDIUM).
  3. Effort (LOW).
  4. Time to make the change (LOW).

Good plan E2

The plan: Make /handoff name its files when it commits

What it's about

At the end of a session, /handoff writes the session's notes into a file and commits it. It stages its own file by name, then runs a plain git commit. A plain commit saves everything staged, not just what this step added. And a handoff often runs while another session is working in the same folder.

Why it's a good plan

If another session has staged a half-finished change, the handoff's notes commit takes it too, and it goes into the history without anyone reviewing it. The sister routine, /commit, already prevents this by naming its files on the commit line, and its instructions say why. The fix is to do the same in /handoff, and in the script that runs that step in this repo.

Think of it like this

Two people share one copy-shop tray. One hands over their pages and says "copy these three". The other puts their page on the tray and says "copy everything on the tray", so a colleague's half-finished draft goes out with it. The fix is to name your pages, as the first person already does.

The question, word for word

Decision

In the handoff instructions' step 5 (espalier/assets/claude/commands/handoff.md) and the script that runs that step in this repo (scripts/handoff_mechanics.py), name the files on the git commit line, as the /commit instructions already do.

Priorities (second message)

  1. A handoff never commits someone else's work (HIGH).
  2. The handoff steps stay simple (MEDIUM).
  3. Effort (LOW).
  4. Time to make the change (LOW).

The evidence that decides it

  • (During a merge git refuses a path-limited commit. Stop there and ask; do not fall back to a broad one.)commit.md:109–111The one catch, which /commit already handles.

Why these paths: the working copies of both routines sit in the .claude folder, which the models' copy leaves out. Identical copies in espalier/assets/claude/commands/ stay, so the models read the same words.

Tough call E3

The decision: Should Bash refuse the same deletes as PowerShell?

What it's about

On Windows the AI can run commands through two tools, PowerShell and Bash. When it tries to delete a folder near the top of a drive, such as C:/work/old or C:/Windows/System32, PowerShell refuses outright. Bash only asks "are you sure?", and the AI gets past that by asking again. Bash's warning even says the check "hard-blocks … shallow system paths", which isn't true on Bash. The plan: make Bash refuse too.

write_guard's answer to one plain recursive delete on Windows, at this snapshot (task-packs/FORWARD_LEDGER.md:1647 and :1655; docs/HOOKS.md:639–643)
FolderPowerShellBash todayBash, if it matched
C:/Windows/System32RefusesAsksRefuses
C:/work/oldRefusesAsksRefuses
D:/data/cacheRefusesAsksRefuses
Inside the project or home folderAsksAsksAsks
Inside a temp folderAsksAsksAsks

The trade-off

Making Bash refuse gives one answer per folder, whichever tool runs the delete, and it stops a slip on a system folder instead of only questioning it. But ordinary folders such as C:/work/old and D:/data/cache would be refused too, with no way past inside the session. My own rule ranks that cost first: false alarms and friction outrank closing loopholes. The same rule says the threat is mistakes, not malice, and a slip on System32 is exactly a mistake. So the rule pulls both ways.

Think of it like this

A building has two doors to the same machine room. The front-door guard flatly refuses anyone heading for the main wiring closet. The back-door guard asks "are you sure?" and lets you through if you say yes twice. Make the back door refuse too, and a careless slip at the wiring closet gets stopped. But the electrician doing ordinary work in the closets nearby gets turned away as well, and can't be let in on the spot; it takes a trip to the office.

The question, word for word

Decision

On Windows, make the Bash tool refuse the same deletes near the top of a drive that the PowerShell tool already refuses (like C:/work/old or C:/Windows/System32), so both tools give the same answer.

Priorities (second message)

  1. Don't block ordinary work (HIGH).
  2. A slip must never wipe a system folder (HIGH).
  3. The two tools and their warnings agree (MEDIUM).
  4. Effort (LOW).

## Step 2: Alternatives

**ALTERNATIVE A: deadline inside the guard that blocks when it runs out (outer limit stays at 5 s)**
- **CORE DIFFERENCE:** when a check runs out of time, the guard itself refuses the action, instead of Claude Code letting it through.
- **SKELETON:**
  ```
  write_guard.py main():
    data = read_stdin()
    if tool_name not in MUTATION_TOOLS and not mcp:  # existing cheap filter, unchanged
        return allow
    # Windows has no signal.alarm, and a thread can't interrupt a running regex,
    # so the slow matching runs in a child process
    child = spawn([sys.executable, "-I", "_guard_worker.py"], stdin=data)
    try:
        out = child.communicate(timeout=INNER_BUDGET)  # e.g. 3.5 s, under the 5 s limit
        emit(out)
    except TimeoutExpired:
        child.kill()
        audit("pretooluse_blocked_guard_deadline", tool=tool_name)
        emit(deny("guard could not decide in time; split the command or use a script file"))
  harness_config: write_guard timeout stays 5 (and must stay above INNER_BUDGET)
  ```
- **BUYS:** a slow check becomes a refusal that gets logged, not a silent pass.
- **COSTS:** an extra Python start on every guarded call (Bash, PowerShell, writes, MCP), and the worst-case delay is still about 3.5 s.

**ALTERNATIVE B: a cost check before any regex runs (outer limit stays at 5 s)**
- **CORE DIFFERENCE:** limit how expensive an input can be before matching starts, instead of limiting the time afterwards.
- **SKELETON:**
  ```
  write_guard.py, before the Bash/PowerShell checks:
    cmd = tool_input["command"]
    cost = (len(cmd),
            count_separators(cmd),            # ; | && etc.
            max_repeated_prefix(cmd),         # eval / sh -c / env -i runs (CHANGELOG:1618 class)
            count_unmatched_groupers(cmd))
    if exceeds(cost, CAPS):                   # caps set from corpus + test_redos payloads
        audit("pretooluse_blocked_input_cost", ...)
        return deny("command too complex to vet; put it in a script file")
    ... existing regex checks, now only on inputs within the caps ...
  tests: test_redos asserts each worst-case payload is either over the caps or under budget
  ```
- **BUYS:** the inputs known to be slow are refused in milliseconds, without an extra process.
- **COSTS:** long legitimate commands, like heredocs, get refused. And slow inputs that stay under the caps still depend on the 5 s limit, which lets them through when it expires.

Fairness check: not triggered. The proposal is weaker than both alternatives on the one HIGH criterion.

## Step 4: Verdict

- **VERDICT:** SPLIT
- **CONFIDENCE:** MEDIUM
- **EVIDENCE:** FACT that a timed-out guard lets the call through (Claude Code's documented behaviour, quoted in the repo). INFERENCE that the guard runs in about 0.3 s; nothing in the repo measures it.
- **REASONING:** On criterion 1, the 1 s cut is only safe if no input, including a cold start on Windows or a busy machine, takes longer than about 0.5 s. The repo doesn't know that. Before the regex fixes, some inputs took about 2.5 s, which the docs called "latency, not fail-open" only because they finished under 5 s (`bench/RESULTS.md:138`). Those fixes may have made every path fast, in which case the cut costs nothing on criterion 1 and wins criterion 2. If they didn't, the cut quietly turns slow checks into allowed actions, and you'd want A, or 5 s plus B. The repo's own rule is limit = 2 × p99 (`FAILURE_MODES.md:4195`), so the decision depends on a number nobody has measured. No conclusion here rests on charitable scores.

**What would settle it:** run `write_guard.py` as a subprocess, exactly as Claude Code does, over the bench corpus plus the `tests/test_redos.py` worst-case payloads. Do it on Windows through the `py -3` launcher, both cold and with a parallel pytest loading the machine, and record p99 and max wall time.
- If max × 2 is under 1 s, make the cut.
- If not, keep 5 s and decide between A and B.
