How the test works

Three kinds of question

Good plan

The repo's own files back the plan. The right reply is yes, go ahead.

Bad plan

The repo's own files sink the plan. The right reply is no, with the reason.

Tough call

All the facts are in the repo and both choices hold up. The right reply says it's close and helps you weigh it.

Three versions of every question

Each model gets each question three times, in a fresh session each time. Only the first message changes.

  • Plain requestChallenge this decision before we lock it in: [decision].
  • Short promptChallenge this decision before we lock it in: [decision]. Read the project files it depends on, and end with a verdict: stay, pivot or split.
  • The command/decision-challenge [decision]

Then every version gets the same second message: the user's priorities, each marked HIGH, MEDIUM or LOW, ending with "Go on." The reply that's marked is the AI's answer to that second message.

What that second message means. In real use, nobody sends their priorities to a plain request unless it asks for them; only the command asks. So this test compares how the three versions reason when they get the same information, which is generous to the two without the command. As a second reading, decided after the runs, I also marked the first reply of those two versions on its own, where a real conversation would usually stop.

Why a short-prompt version? It asks for two of the command's moves, reading the files and ending with a verdict, in a prompt anyone can type. If it does as well as the command, the results say so, and you can use the prompt.

How a reply is marked

  • ✓
    Right call. What counts is written on each card.
  • ✗
    Wrong call. The wrong side, or treating a settled question as open, or an open one as settled.
  • –
    No call. No verdict, or pros and cons with no help deciding.

A few rules hold on every card. On a Bad plan, a ✓ needs the real reason, not a general warning. On a Good or Bad plan, a middle way or "run a test first" is ✗ when the files already settle it. On a Tough call, a lean either way can earn ✓, and so can a middle way argued as a trade. Each turn has a 30-minute limit; a reply cut off by it is marked on what it had said by then.

Who marks the replies

Two AI models mark every reply, each on its own: Claude Sonnet and GPT-6 Luna. They aren't told which version or model wrote it, but what the user typed shows the version, and the agent's tool-call style can show whether it ran in Claude Code or Copilot. Where they disagree, Claude Opus decides, also without being told. I marked 15 Tough-call replies myself, shuffled and without names, starting with ones the two markers disagreed on.

The repo: sibling-site-drift-lab

A lab that tests whether a step-by-step checking routine stops AI coding agents from leaving related files out of date: you change a limit in the code, and forget the test or the docs that mention it. Its first round gave agents 9 small coding tasks, each with a trap of that kind, and ran every task 5 times under four setups. That came to 180 runs.

The research is ongoing and planned for future release, so each card quotes the lines that decide its question.

Good plan D1

The plan: Fix the grader that marked correct work as wrong

What it's about

One task, B007, says the export limit changed from 3 to 5 per day: update the code and the tests. The grader checks three things. The third is that the limit's name appears in one particular test file, tests/test_routes.py. That file only tests a web route. It has never tested the limit.

Why it's a good plan

9 of the round's 10 failed runs are this one task. Every one of those 9 wrote its new limit test in a new file and was marked failed. Every run that put the test in the old file passed. The work was fine; the grader only looked in one place. So the grader gets fixed before the task is used again.

Think of it like this

An answer key says the answer has to be written in box 3. A student writes the right answer in box 4, where there's more room, and loses the mark. Nine students in a row lose it the same way. You fix the answer key before you give that test again.

Bad plan D2

The plan: Triple the runs on the same nine tasks

What it's about

The first round couldn't show whether the system helps, because almost every run got its task right, with help or without. The tempting fix is to run each task more often.

Why it's a bad plan

Without help, agents failed only 3 of 45 runs, and 2 of those 3 were the grader problem from card D1. Showing that the system halves a failure rate that low takes roughly 650 to 700 runs per group. That's about 15 times today's 45; tripling gets to 135. The lab's own note, written before the round, gives the reason: the tasks are too easy. More runs of easy tasks only confirm they're easy. What's needed is harder tasks.

Think of it like this

You want to know whether a new study method helps, but the test is so easy that everyone scores 95 to 100%. Giving the same easy test three times as often won't show a difference. You need a harder test.

Tough call D3

The decision: Drop the full-system group?

What it's about

The full system (C4) costs the most per run: $1.10, against $0.42 with no help. On the main result, no setup beat any other, because the tasks were too easy. On behaviour, meaning how often agents checked their work and fixed problems, C4 landed between the two basic setups every time. ## Step 2: Alternatives

**ALTERNATIVE A: mutation-kill oracle**
- **CORE DIFFERENCE:** A limit test passes the grader if the tests under `tests/` pass on the agent's tree and fail when the limit is reverted to 3. Where the test lives and what it's called don't matter.
- **SKELETON:**
  ```
  oracle: {type: "mutation_kill", role: "goal", path: "tests",
           mutate: {path: "app/limits.py", old: "= 5", new: "= 3"}}
  _check_oracle_inner, op == "mutation_kill":
      tmp = copytree(root)
      base = run([python, -m, pytest, -q, tmp/tests])     # must exit 0
      _apply_mutation(tmp, oracle["mutate"])               # reuse existing helper
      mutant = run([python, -m, pytest, -q, tmp/tests])   # must exit != 0
      pass = base.returncode == 0 and mutant.returncode != 0
  _validate_oracle: require "mutate" with path/old/new
  tests: tests in test_limits.py pass; tests in test_routes.py pass;
         an import-only mention fails; a test asserting == 3 fails
  new case file B007 v2 (frozen v1 left untouched)
  ```
- **BUYS:** It checks whether the agent's tests actually guard the limit, so correct work passes wherever it is written and decorative mentions fail.
- **COSTS:** It's a new oracle type that runs pytest twice. Round-one runs can only be compared after rebuilding their final trees from transcripts, which hasn't been tried.

**ALTERNATIVE B: seed a stale test that already exists**
- **CORE DIFFERENCE:** Redesign the case so the drift is a limit test that already exists and is now out of date, instead of a test the agent has to create in a place we chose.
- **SKELETON:**
  ```
  mutations += {op: "write", path: "tests/test_limits.py",
                content: "from app.limits import MAX_BULK_EXPORTS_PER_DAY\n
                          def test_limit(): assert MAX_BULK_EXPORTS_PER_DAY == 3\n"}
  (the shared shop-mirror fixture is untouched; seeding is per case)
  oracles:
    keep: docs/policy.md contains "**5 bulk exports per day**"     (preserve)
    keep: run_command MAX_BULK_EXPORTS_PER_DAY == 5               (goal)
    replace path oracle with: run_command [python, -m, pytest, -q, tests]  exit 0  (goal)
  ground_truth.obligations: "update stale test sibling"
  new case id B007b (B007 v1 remains frozen)
  ```
- **BUYS:** It measures the coupled-representation drift the probe note describes, using oracle types that already exist (`write` mutation, `run_command`).
- **COSTS:** It's a different task, so it can't be compared with round one. Agents that run the tests are told about the stale sibling, which probably makes the case easier.

## Against your criteria

1. **The grader marks correct work as correct (HIGH).** Both new graders accept all 20 real runs. The proposed one also accepts a test that checks nothing and a test that still asserts the old limit. A grader that passes those can't be trusted to judge work, so the enforcement check wins here.
2. **Comparable with round 1 (MEDIUM).** Tie. Both rescore round 1 the same way, 20 of 20 B007 runs passing, so the two rounds can be compared once round 1 is rescored. Without rescoring they can't: round 1 recorded 9 B007 failures that were really grader errors, and those are 9 of the campaign's 10 imperfect runs. Report the rescoring as a labelled post-hoc analysis alongside the original numbers, not instead of them.
3. **Effort (LOW).** The enforcement check probably costs less. It fits the existing `run_command` oracle type as an inline script, the same way B007's limit check already works. The proposed grader needs a new oracle type that searches a folder, plus validation and tests for it in `benchmark.py`.
